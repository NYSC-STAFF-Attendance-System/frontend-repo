# NYSC Staff Attendance — Staff Frontend

Mobile web app for NYSC staff to record attendance by scanning a permanent QR
code at their office. Attendance is only recorded when the person is physically
at the office, on their own registered phone.

**This repository currently contains the staff side only.** The admin dashboard
(Superuser and Office Admin) is separate work — see
[For the admin dashboard](#for-the-admin-dashboard) below for how the two fit
together.

## Running it

```bash
yarn install
yarn dev            # http://localhost:3000
```

### On a phone

Geolocation only works in a secure context, so plain `http://192.168.x.x:3000`
will fail at the location step on `/scan`. Use HTTPS:

```bash
yarn dev --experimental-https -H 0.0.0.0
```

This downloads `mkcert` and generates a self-signed certificate — approve the
operating-system prompt when it appears. Then open `https://<your-LAN-ip>:3000`
on a phone on the same wifi and tap through the certificate warning
(**Advanced → Proceed**).

Find your LAN IP with `ipconfig` (Windows) or `ifconfig` (macOS/Linux).

### Checks

```bash
npx tsc --noEmit     # types
npx eslint .         # lint
npx next build       # production build — also proves the Suspense boundaries
```

## Demo data

Everything is served by a mock client. No backend required.

| Purpose | Value |
|---|---|
| Staff ID | `NYSC/FCT/0842` |
| Password | `password123` (any 8+ characters) |
| Banned account | `NYSC/FCT/0619` |
| Already-registered staff ID | `NYSC/FCT/0619` |
| Scan token | `qr_fct_hq_9f2a7c` |

Passwords that force a specific login failure: `wrongdevice`, `unverified`,
`offline`.

**`/dev/qr`** renders the office poster as it would be printed. Display it on a
laptop, scan with a phone, and you land on `/scan` with the token in the URL.
It builds the URL from wherever it is running, so it works on localhost, over
HTTPS on a LAN, and deployed, with nothing to edit. It is a demo tool — the real
poster is generated by the admin dashboard.

### Forcing scan states

Several outcomes cannot be produced by driving the mock normally — you cannot
stand outside a fictional geofence. Append to the `/scan` URL:

```
/scan?t=qr_fct_hq_9f2a7c&force=outside_geofence
```

`force` accepts: `signed_in`, `signed_out`, `already_complete`,
`outside_geofence`, `wrong_device`, `account_banned`, `office_inactive`,
`invalid_token`, `rate_limited`, `offline`, `error`.

`forceResolve` does the same for the token-resolution phase and accepts
`invalid_token`, `rate_limited`, `offline`, `error`.

Location failures are reached through DevTools → Sensors → Location, or by
blocking location for the site in the address bar.

Demo session state lives in `sessionStorage`, so scanning the QR continues the
same day. Closing the tab starts a fresh demo.

## Architecture

Data flows one way, and screens only ever talk to the layer directly below them.

```
types/          the shape of every record — the contract
   ↓
lib/mock/       fixtures matching those types
   ↓
lib/api/        one `api` object; mock or real, chosen by an env flag
   ↓
app/            screens, which know nothing about where data came from
```

### `lib/api/`

Every screen imports one object:

```ts
import { api } from "@/lib/api";
```

`lib/api/types.ts` defines `ApiClient` — the whole surface the staff app may
touch. `mock.ts` and `real.ts` both implement it. `index.ts` picks between them:

```ts
const useMock = process.env.NEXT_PUBLIC_USE_MOCK_API !== "false";
```

Mock is the default, including when the variable is missing, so a fresh clone
runs with no configuration and no backend. Pointing at the real API is a
deliberate opt-in — set `NEXT_PUBLIC_USE_MOCK_API=false` in `.env.local` (see
`.env.example`).

`real.ts` is stubbed. Every method already has the correct signature and the
endpoint paths are listed at the top of the file. Wiring it means writing the
requests and mapping responses onto the result unions. **No screen changes.**

### Nothing throws

Every API method resolves to a discriminated union describing what happened,
including failure:

```ts
type LoginResult =
  | { kind: "success"; staff: StaffProfile }
  | { kind: "invalid_credentials" }
  | { kind: "wrong_device" }
  | { kind: "account_banned" }
  | { kind: "email_not_verified"; email: string }
  | { kind: "rate_limited"; retryAfterSeconds: number | null }
  | { kind: "offline" }
  | { kind: "error"; message: string };
```

A `try`/`catch` you forgot to write fails silently at runtime. A union the
compiler makes you unpack fails at build time, at the exact line.

Data rides on the branch it belongs to. `signed_in` carries an `AttendanceDay`;
`outside_geofence` carries nothing, because nothing was recorded. Reading
`.day` on the wrong branch is a compile error.

### `assertNever`

Every switch over a union ends with it:

```ts
default:
  return assertNever(outcome);
```

If all cases are handled, TypeScript narrows the value to `never` and it
compiles. Add a case to the union later and every switch that forgot it fails
the build. This is what stops `/scan` rendering an empty panel at an office door.

## Routes

| Route | Access | Notes |
|---|---|---|
| `/` | public | entry point |
| `/login` | public | staff sign in; sends `device_id` |
| `/register` | public | three-step claim flow |
| `/verify-email` | public | serves `?email=` and `?token=` |
| `/forgot-password` | public | |
| `/reset-password` | public | reads `?token=` |
| `/home` | protected | today at a glance |
| `/scan` | protected | reads `?t=`, the attendance screen |
| `/history` | protected | records and statistics |
| `/profile` | protected | record and device binding |
| `/profile/password` | protected | |
| `/blocked` | public | reads `?reason=banned\|device` |
| `/dev/qr` | public | **demo tool**, delete once the dashboard exists |
| 404 | — | `app/not-found.tsx` |

`app/(protected)/` is a route group — the brackets organise files without
appearing in the URL, so `/home` is still `/home`. Everything in it gets
`AuthGuard`, the top app bar and the bottom navigation.

**`/scan` sits outside that group deliberately.** It gets the same auth guard but
neither bar, because the sign-in button has to be reachable without scrolling at
375px and the two bars would take 108 pixels of the fold.

## Product rules that shape the code

These are not preferences. They come from the product description and the phased
build plan, and the code is arranged so they are hard to break by accident.

**GPS is requested only at attendance time.** Never on registration or login.
`/scan` resolves the token and loads today first; a dead token, a dead office or
a day already complete all stop before the permission prompt. The prompt is also
tied to a deliberate tap — asking on page load trains people to deny it, and a
stored denial never re-prompts.

**One phone per staff member.** A `device_id` is generated at registration,
stored in `localStorage` (`lib/device.ts`), and sent on every login and
attendance call. Staff cannot change it; only an admin can reset the binding.
This is not a security boundary on its own — the backend refuses the mismatch.

**The backend owns the geofence.** `Office` deliberately has no coordinates and
no radius. The frontend sends lat/lng and renders the answer. A value the phone
can read is a value the phone's owner can change.

**The backend owns lateness.** `AttendanceDay.status` and `minutesLate` arrive
as data. Nothing in the app compares a timestamp against a resumption time, sums
days, or works out a percentage. Two implementations of the same arithmetic
would drift, and the server holds the version that appears in admin reports.

**Timestamps come from the server, never the device clock.** They are kept as
ISO strings and never parsed into a `Date`, because a `Date` is re-expressed in
whatever timezone the phone is set to. `lib/format.ts` slices the string
instead. `TodayResult` also returns the server's idea of today's date, so a
phone in the wrong timezone cannot disagree about which day it is.

**One sign in and one sign out per calendar day**, Africa/Lagos.

**Registration is a claim, not a sign-up.** An admin creates the staff record
first. Step one looks it up; the form never lets a staff member set their own
name, office or department.

## Conventions

**Light only.** Dark mode is deliberately not supported: one colour scheme means
one set of contrast ratios to verify, and the geofence states have to be
unambiguous. Locked in three places — `color-scheme: light` and explicit
`html`/`body` colours in `app/globals.css`, and `colorScheme: "light"` in the
root layout's viewport export.

Do not add `@media (prefers-color-scheme: dark)` anywhere, and do not put a
`.dark` class on `html` or `body`. **Keep the `@custom-variant dark` line in
`globals.css`** — it pins every `dark:` utility to a class that never appears.
Remove it and those utilities revert to following the operating system, quietly
reintroducing dark mode.

**Colour tokens** live in `app/globals.css`, not a config file (Tailwind v4).
`--primary` is NYSC green, `--success` is a confirmed sign in or out,
`--destructive` is a refusal, `--warning` is Late and Incomplete — which are
neither.

**`useSearchParams` needs a Suspense boundary.** It cannot be read during
prerendering, so `next dev` works and `next build` fails. The boundary must sit
*above* the component reading the URL, which means it cannot be in the same
file. Affects `/scan`, `/verify-email`, `/reset-password` and `/blocked`, each
split into a server `page.tsx` holding the boundary and a client view beside it.

**Button sizes.** `size="xl"` is 48px and reserved for the one primary action on
a screen — Sign In, Sign Out, Continue, Submit. Not for secondary buttons,
cancel links or icon buttons. If everything is 48px, nothing reads as the main
action.

**Inputs are `h-12` and `text-base`.** The 16px font is what stops iOS Safari
zooming the page when a field receives focus, which then stays wrong for the
rest of the session. Do not reduce it.

**Base UI uses `render`, not `asChild`.** Most shadcn examples online assume
Radix:

```tsx
<Button render={<Link href="/login" />} size="xl">Go to sign in</Button>
```

**Comments explain why, not what.** Every component has a short block saying what
it is and where it is used; non-obvious logic says why the check exists.

## Open questions for the backend

Answers to the first three change type definitions.

1. **Attendance status values on the wire.** The PRD names Present, Late, Absent,
   Checked Out and Incomplete in prose. Assumed lowercase snake_case:
   `present`, `late`, `absent`, `checked_out`, `incomplete`. Is the set closed?
2. **Resumption time and grace period — per office or global?** The build plan
   describes one global `AttendanceSettings` record (radius, timezone) and never
   mentions resumption time. The PRD says "configurable by the administrator"
   without saying at what level. Assumed global — see `types/settings.ts`.
3. **Exact fields on an attendance record**, and which can be null. Is
   `minutesLate` returned at all, or only the status?
4. **Is there a staff statistics endpoint?** Days present, days absent, late
   arrivals, early departures, attendance percentage, average arrival and
   departure time, consecutive days, for a date range — one call or assembled?
5. **Department shape** — nested object with id and name, or a flat string?
   Assumed nested, because department is filterable.
6. **Timestamp format** — ISO 8601 with a UTC offset, or local time with none?
7. **Percentage and averages** — is percentage 0–100 or 0–1? Are average times
   `"HH:mm"` strings or minutes since midnight?

Two assumptions worth confirming: a day that is both late and completed keeps
`status: "late"` rather than becoming `checked_out`; and `minutesLate` is
measured from the resumption time, not from the end of the grace period.

## For the admin dashboard

Suggested split, open to discussion:

**Admin lives under `/admin/*`. Staff stays at the root.** The reason is the QR
codes. Those posters are printed once and stay on office walls; whatever path
`/scan` lives at is baked into physical paper. `/scan?t=…` is the URL you want
there, and if it ever changes, someone has to reprint nationwide. Staff are also
the far larger group, on phones. Admins are a handful of people on desktops who
can live with a prefix.

**`/login` is the real collision.** Staff login hits `/api/staff/login/` with a
`device_id` and is refused on the wrong phone. Admin login hits
`/api/auth/login/` with no device binding. They cannot be one page — suggest
`/login` for staff and `/admin/login` for admin.

**Shared, and worth keeping shared**

- `types/` — `Office`, `Department`, `AttendanceDay`, `AttendanceStatus`,
  `AttendanceSettings` are the same records both halves render. One definition
  means one file changes when the backend answers the questions above.
  `StaffProfile` is staff-side; admin will want a fuller staff type with device
  and ban state.
- `components/ui/` — an `xl` size was **added** to `Button`; nothing existing was
  changed. Please extend the same way rather than altering defaults.
  `components/ui/input.tsx` is tuned for mobile (`h-12`, `text-base`) — if that
  is wrong for dense desktop tables, add a size variant.

**Needs a joint decision: dark mode.** The light lock described above is
app-wide. If the dashboard wants dark mode, the lock moves off `:root` onto a
wrapper around the staff routes and `colorScheme` comes out of the root layout.
Cheap now, expensive once both halves are built.

**Separate API clients.** `ApiClient` is staff-only by design — nothing on it can
reach an admin endpoint. Suggest `lib/api/staff/` and `lib/api/admin/`, sharing
the env flag and the axios instance.
